# P0: реализуемость восстановления между сессиями

## Вывод

Статические источники показывают, что восстановление из сохранения после рестарта миссии технически предусмотрено опубликованным checkpoint-модом в пределах управляемого им потока: команда Reload вооружает маркеры, хост выходит в лобби и стартует ту же миссию, loader на каждом процессе подменяет пути загрузки. Но исходники прямо ограничивают автоматическую функцию текущей mission session. Для сценария «игра одного участника упала/закрылась, затем игроки создали новое кооперативное лобби» работоспособность не подтверждена.

## Что блокирует сценарий аварии

1. **Нет протокола аварийного возобновления.** Маркер reload создаётся обработчиком команды Reload, которая должна быть исполнена в живой сетевой сессии. После процесса аварии этот процессный/временный маркер может отсутствовать. Новый лобби самостоятельно не обнаруживает checkpoint и не согласует загрузку.
2. **Checkpoint лежит на peers отдельно.** Код вызывает локальный `CreateSave` на каждом участнике и пишет отдельный серверный архив. Пересылки единого снимка нет. Если клиент завершился до команды сохранения/фиксации файла или потерял локальную копию, остальные файлы не восстановят неизвестную клиентскую специфичную информацию автоматически.
3. **Не доказана достаточность серверного снимка.** Не исследованы фактические поля архива и не проверено, могут ли все клиенты загрузить серверный файл. Поэтому нельзя заключить, что клиентские архивы избыточны или обязательны для самого движка.
4. **Player mapping хранится в памяти.** Для повторной загрузки код держит базовые player IDs, число игроков и mission path в глобалах процесса, затем переносит значения в временный marker. Аварийный перезапуск теряет эти данные без отдельного постоянного metadata-файла.
5. **Состав новой сессии может отличаться.** Новый host/client порядок, число участников, player slots, миссия, карта, версии игры и модов требуют проверки. Снимок не содержит опубликованного протокола для согласования этих значений.
6. **Состояние миссионных скриптов неполное.** Заявленная известная потеря: активная script sequence, прерванная в середине, после загрузки не продолжается. Значит, цель восстановления должна задавать допустимость скриптового расхождения.
7. **Транзакционная полнота не установлена.** Нет подтверждённого общего commit/ack от всех peers, который бы доказывал, что checkpoint завершён и пригоден для восстановления на каждом участнике.

## Единый серверный snapshot или snapshots каждого клиента?

Ответ сейчас: **неизвестно**. Исходники демонстрируют только выбранный автором дизайн «каждый peer сохраняет локально»; они не доказывают, что движок требует peer-specific archives. Требуется эксперимент: сохранить архивы A, B и server в одной синхронной точке, безопасно скопировать их, затем при равных условиях пробовать групповые варианты загрузки и сравнивать результат. До успешного эксперимента нельзя отказываться от снимков каждого peer.

## Минимальный технический вывод для P1

P1 должен начинаться с read-only прототипа протокола чекпоинта и тестового harness, без игрового patch: метаданные с mission/map ID, game build, mod fingerprint, player roster/slot mapping, quant/clock, идентификатора checkpoint, ролей peer, SHA-256 и статуса завершённой записи каждого локального архива. Новый lobby должен получить копии всех подтверждённых требуемых архивов, проверить совместимость и только затем разрешать загрузку. Если эксперимент докажет, что единый серверный snapshot достаточен, протокол можно упростить. Не реализовывать подключение к живой сессии на P1.

Это архитектурное предложение для следующего этапа, не утверждение о реализованной совместимости API движка.
