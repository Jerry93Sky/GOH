# Первый запуск с другом — V0.2.1

Эта сборка готовит локальные маркеры Coop Checkpoint и проверяет файловый набор. Она не подтверждена в игре; TEST-A и TEST-B остаются `NOT_RUN`. Не используйте её в кампании без резервной копии профилей.

## До запуска

1. Оба игрока используют одинаковые версию игры, миссию и набор модов. Закройте игру до импорта файлов.
2. Каждый участник сохраняет свой исходный профиль и отдельно копирует `coop_ckpt.sav`; хост сохраняет также `coop_ckpt_srv.sav`.
3. В архивной копии участников проверяются точные размеры и SHA-256. Хосту нужны оба его маркера: client marker для игрового процесса и server marker для локального сервера. Запускайте менеджер отдельно на каждом компьютере.

## Сбор данных

1. На вкладке «Наблюдение» каждый выбирает свой профиль. Укажите точный лог `goh_coop_checkpoint_call_to_arms.exe.log`. Хост отдельно указывает `goh_coop_checkpoint_call_to_arms_server.exe.log`, созданный серверным процессом.
2. Эти имена подтверждены опубликованным контрактом Coop Checkpoint. Путь marker берётся из родительского каталога выбранного лога, то есть из каталога `GetTempPathW`, который использовал процесс. Windows обычно использует TEMP/TMP процесса; если server process пишет в другой каталог, хост должен выбрать именно его лог. Нельзя подменять его игровым логом или каталогом TEMP менеджера.
3. Используйте «Собрать доступные метаданные» и передавайте provenance JSON вместе с соответствующей копией архива. Не вводите отсутствующие runtime значения вручную.
4. Хост собирает отдельные client и server источники. Каждый клиент сохраняет свои client данные и передаёт ZIP-пакет хосту. Передайте также логи всех участников.

## Протокол общей точки

Локальное `checkpoint #N` — счётчик процесса, не общий ID. До подготовки marker заведите JSON по схеме `goh-checkpoint-consistency-protocol-v1`: `checkpoint_id` (назначенная участниками подпись события), `package_checkpoint_id` (точное ID выбранных recovery-файлов), `mission_id`, `host_player_id`, `operator_confirmed_same_checkpoint_event: true` после устного сверения, и `participants`. Для каждого участника нужна запись `participant_id`, `process_role` (`client`; отдельно `server` для локального сервера хоста), `source_log_path`, `source_log_sha256`, `internal_mission_path`, `virtual_archive_base_path`, `local_checkpoint_sequence`, `quant_clock` и `observed_at_utc` из соответствующих файлов/логов. Не копируйте значения одного компьютера для другого. Такой протокол фиксирует операторское сопоставление, но не является доказательством движковой синхронизации.

## Новое лобби и маркеры

1. Сверьте комплект пакетов, хост ID, архивы, игровой build и fingerprints. Без полного ручного протокола preflight заблокирован.
2. Создайте новое кооперативное лобби той же миссии. Все участники должны подтвердить готовность до создания marker.
3. На каждом клиенте подготовьте только client marker; на компьютере хоста подготовьте отдельно client marker и server marker, каждый из своего точного process log. Если каталог server log не доказан, не продолжайте.
4. Перед подтверждением проверьте в окне источники метаданных, архив, путь marker и результат preflight. TEMP/TMP процесса должен оставаться тем же с момента записи лога. Marker действует 15 минут; активируйте их непосредственно перед стартом.
5. Зафиксируйте фактический результат, скриншоты/логи и изменения миссии. Не помечайте TEST-A/B как пройденные, если испытание не завершено в настоящей игре.

При любой неоднозначности отмените подготовку, сохраните исходные файлы и передайте диагностический пакет разработчику. Менеджер не устанавливает DLL, не меняет игровые ресурсы, сетевую аутентификацию или протокол.
