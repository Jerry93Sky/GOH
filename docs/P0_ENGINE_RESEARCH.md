### Сохранение и синхронизация

- Mission patch добавляет кнопки Save/Reload и триггеры к читаемому тексту миссии в памяти. Патч также оборачивает штатные `{"autosave"}`. Исходник говорит, что игровой ресурс на диске не изменяется.
- DLL перехватывает исполнение `eCmd_autosave`: по комментарию, штатная команда отключена в network session. В сетевом случае вызывается `Save::CreateSave` непосредственно при исполнении команды на quant.
- На сервере исполнения mission script команда `autosave` инициирует сохранение серверной копии и отправляет `eSceneActionCommand` с сетевым ID `0x67`. Каждый клиент, исполняя команду в собственном потоке команд, отдельно вызывает `CreateSave` и пишет собственный архив. Код задаёт отдельные имена `coop_ckpt.sav` для клиента и `coop_ckpt_srv.sav` для локального сервера. Передачи единого архивного снимка по сети в исследованной реализации не найдено.
- Авторские комментарии описывают сетевой quant как 20-миллисекундный шаг, одинаковый поток команд и сохранение на главном/симуляционном потоке. `goh_common.h` находит данные quant через сигнатуру `SIG_FIXED_BRANCH`; `coop_checkpoint.c` читает clock по смещению `eQuantControl + 0x48` и пишет его в лог. Это сообщения/объяснения к reverse-engineered коду, а не независимое измерение сетевого протокола.
- Сохранение скриншота пропускается в отдельных местах: клиентский D3D-р render может блокировать simulation thread, у dedicated server нет renderer. Для server save временно очищается указатель на выполняющийся script thread, потому что serializer trigger actions иначе не пишет действия. В исходнике есть обход сериализации SDL trigger blocks.

### Триггеры, загрузка и сетевой состав

- Reload-команда использует `achievement` и специальное значение `nation coop_ckpt_reload`; обработчик пишет per-process marker в `%TEMP%`. Этот маркер содержит путь миссии и путь архива, опционально базовый player ID и число игроков. Срок жизни маркера — 15 минут.
- При следующем старте соответствующей миссии hook scene loader заменяет обычные пути путями архива сохранения, пользуясь блоком построения путей штатной загрузки. Это именно новая загрузка сцены, не attach/join к уже работающему серверному миру.
- Для повторной сессии код корректирует quant clock и старт серверного master quant scheduler, поскольку сетевой слой нового матча иначе может считать команды запоздавшими. Клок сцены сохраняется отдельно, поскольку entity timers абсолютны.
- Людские player IDs, согласно комментарию, назначаются после максимального owner ID сцены; после reload они смещаются. Реализация запоминает исходный диапазон в памяти процесса и переназначает owner IDs при загрузке. Это состояние процесса и миссии, которое требует отдельного решения при аварийном перезапуске.
- Миссионный patch после загрузки вызывает `autoassign` для coop-слотов, чтобы восстановить контроль подразделений.
- Есть специальный обход erase в entity-id map для отсутствующих после загрузки ID; автор указывает на риск повреждения heap при выходе из матча.
- Сам README checkpoint явно описывает сохранения как session-only; script sequence, прерванная посередине, после reload не возобновляется. То есть даже успешный scene load не эквивалентен полной сериализации произвольной логики миссии.

Авторский repository README описывает проект как протестированный на v1.067.0. Это зафиксировано как заявление автора, не как подтверждённый нами результат.

### Сигнатуры и безопасный отказ

`common/goh_common.h` реализует сканирование сигнатур по секции кода, чтение через SEH-подобную проверку, запись кода через `VirtualProtect` и entry-hook. Большинство критических поисков требуют ровно одно совпадение; иначе функция не устанавливает соответствующий hook и пишет ошибку. Это полезный принцип fail-closed, но не доказательство безопасности всех патчей: некоторые ветви продолжают работать частично, а бинарные смещения и calling conventions всё равно зависят от сборки.

`build.ps1` собирает `version.dll` proxy и игровые DLL. Опция `-Install` копирует файлы в каталог игры; скрипт отдельно проверяет присутствие `call_to_arms.exe`, для существующего чужого `version.dll` по умолчанию сохраняет его, а замену разрешает только с явным `-ReplaceLoader`. Для нашего проекта такой install путь не создаётся.

## Альтернативный исследовательский инструмент

[coa_script_extender README](https://github.com/NorthHead-Digital/coa_script_extender) и [CMakeLists.txt](https://github.com/NorthHead-Digital/coa_script_extender/blob/d994e1750de1c015ed2557250ab461ece73cd721/CMakeLists.txt) описывают DLL loader, MinHook, SDK, множество адресов/структур, Ghidra-скрипты и пример DLL. Он может быть источником методики для изучения функций и xrefs, но не предоставляет подтверждений о сериализации сетевой сессии или загрузке кооперативного checkpoint. Собственный README прямо помечает offsets/типы структур как приблизительные и предупреждает о несовместимости с обновлениями игры. Вызов hook по RVA и примеры чтения/записи памяти требуют независимой верификации до использования.

## Что не следует выводить

- Одновременный `CreateSave` на каждом peer не доказывает побайтную идентичность архивов или полную синхронность мира.
- Наличие save manager в клиенте и сервере не доказывает перенос снимка между игроками.
- Возможность loader загрузить файл из archive path не доказывает, что новый матч принимает старый save, или что все peers завершают load без desync.
- Документированный автором тест на GoH 1.067.0 не был воспроизведён в этой среде.

## Окружение текущего анализа

Проверены несколько стандартных Steam путей установки, Steam registry paths и процессы `call_to_arms.exe` / `call_to_arms_server.exe`: игра не найдена и не запущена. Второй игровой клиент недоступен. Нужны два клиента и игровая сессия для динамической проверки.
