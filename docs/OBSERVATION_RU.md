# Наблюдение за контрольными точками (V0.2)

1. Выберите корень конкретного игрового профиля — папку, внутри которой находится `save`.
2. На вкладке «Наблюдение» укажите роль компьютера `HOST` или `CLIENT`. Это ручное заявление оператора.
3. Включите «Наблюдать за сохранениями». Менеджер опрашивает только точные пути `save/coop_ckpt.sav`, `save/coop_ckpt_srv.sav` и уже существующие `goh_coop_checkpoint_*.log` из текущего `%TEMP%`, с интервалом 3 секунды. Появившиеся позже log-файлы требуют перезапуска наблюдателя; два точных `.sav` пути отслеживаются и при появлении после запуска.
4. При изменении известного архива выполняется локальная проверка стабилизации, копирование в `GOH Coop Recovery/checkpoints/observed-local`, SHA-256 до/после копии и сохранение `observation.json`. Исходник не изменяется.
5. Остановите наблюдатель перед сменой профиля. Закрытие программы также подаёт сигнал остановки.

Статус стабильного файла — только локальная файловая эвристика. Строка `checkpoint written` доказывает только выход из локального вызова сохранения; она не подтверждает совпадение файлов у всех участников и сетевой ACK. `checkpoint #N` является последовательностью процесса, а не общим идентификатором, пригодным для сопоставления клиентов.

## Provenance

Каждое извлечённое поле содержит `value`, `status`, `source_path`, `observed_at_utc`, `method`. `MISSING` оставляется пустым. Роль HOST/CLIENT имеет статус `OPERATOR_PROVIDED`. Версия файла игры и SHA-256 исполняемых/модовых файлов показываются на вкладке «Игра»; версия ресурса EXE не считается игровым build без отдельного подтверждения в самой игре.

Опубликованный лог содержит internal mission path, quant checkpoint sequence/clock, player ID base/count, путь локальной записи и marker `reload ARMED` с virtual archive base. Без `reload ARMED` virtual path не выводится из локального `.sav` пути.
