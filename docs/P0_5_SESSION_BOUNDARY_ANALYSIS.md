# P0.5: граница сетевой сессии в Coop Checkpoint

## Границы вывода

Анализ относится к опубликованным исходникам `nicko996/goh-coop-mods` на commit `c2f8d4f2ec90597417ed405f3e4db8c20a8400aa`; код не копировался. Все сведения ниже — статический разбор. Ни один путь восстановления не запускался в игре в этой среде.

## Подтверждено исходниками

| Вопрос | Наблюдение в исходниках | Значение на границе сессии |
|---|---|---|
| Где проверяется marker? | `arm_reload()` записывает `%TEMP%\coop_checkpoint_reload_<role>.txt`. `on_scene_load()` вызывает `read_marker()` только при обычной загрузке сцены (`paths == NULL`), сверяет сохранённый mission path с загружаемой миссией, затем удаляет marker перед загрузкой. `read_marker()` игнорирует и удаляет marker старше 15 минут. | У обычного старта нового лобби marker должен уже существовать в каждом нужном процессе. Одна оставшаяся копия на клиенте не гарантирует, что server и остальные peers вооружены.
| Что лежит в marker? | Две первые строки: mission path и archive path. Дополнительная строка `players <base> <count>` записывается, если значения известны в памяти текущего процесса. Роль кодируется в имени файла: client/game либо server. | Marker — локальный временный sidecar, без общего session/checkpoint UUID или подтверждения полноты участников.
| Как формируется archive path? | После `CreateSave` `remember_checkpoint_path()` копирует выданный игрой путь, отбрасывает `.sav` и добавляет `/`; код отмечает, что loader затем дописывает `map.scn`, `mission.scn`, `game.scn`. | Путь относится к локальной файловой системе и profile конкретного процесса. Согласование путей на новом хосте/компьютере не реализовано manifest-протоколом.
| Как выбирается загрузка? | В `on_scene_load()` путь миссии извлекается из scene. При совпавшем marker строится path block через найденный path builder — тот же, что используется load-from-save. Затем вызывается оригинальный scene loader. `paths != NULL` пропускается без изменений (штатный load game/editor path). | Это перехват старта/загрузки сцены, а не перенос мира во время соединения и не reconnect к уже живой сессии.
| Какие действия зависят от живой сессии? | Reload-запрос передаётся через `achievement`-команду. На client выполняется расписание автоматического выхода; после выхода UI ждёт lobby и вызывает кнопку старта. Server marker используется для проверки, что reload вооружён на сервере. | Автоматический маршрут зависит от работающего client process, работающего host GUI, сетевого lobby/session service и времени жизни marker. Он не является протоколом после полного завершения процессов.
| Как сохраняется quant clock? | При загрузке берётся clock из загруженной сцены (`eQuantControl + 0x48`), для client вычитается 20 мс, значение округляется вниз до секунды; это значение записывается в quant control. | Код предполагает, что server/client clocks при сохранении различаются на один quant. Это требует игрового измерения, особенно при повторном создании сессии.
| Как стартует server scheduler? | Hook `on_scheduler_start()` сначала вызывает оригинал, затем если выставлен `g_master_start`, записывает его в поле scheduler `+0x40`. `g_master_start` задаётся из скорректированного scene clock при reload. | Восстанавливается согласованная нумерация quants для новой сетевой сессии. Нельзя переносить численное значение в другой build без повторного анализа.
| Как сохраняются player IDs? | При обычном старте hook сохраняет `g_players_base`, `g_players_count`, `g_players_mission` в памяти процесса. `arm_reload()` пишет base/count в marker. При загрузке hook ремапит owners актёров по циклической формуле относительно исходного диапазона. | Полный crash до создания marker теряет in-memory player mapping; смена машины/профиля/порядка игроков в новом лобби не обслуживается этим сохранённым диапазоном автоматически.
| Как возвращается контроль подразделений? | Mission patch добавляет trigger `after_reload`, выполняющий `autoassign` для coop-слотов. Player-owner remap выполняется отдельно в hook setter. | Это два разных шага: owner ID сцены и распределение групп игрокам. Их нужно проверять по отдельности после нового lobby.

## Гипотезы для проверки

- Архивы клиента и сервера могут содержать разные поля или иметь разные условия сериализации. Поэтому manifest координатора требует снимок каждого участника и server snapshot; это консервативная проверка комплектности, а не утверждение о требованиях engine.
- Новое lobby с теми же участниками может принять старый mission archive, если всем процессам подать согласованные локальные копии и восстановить clock/roster. В исходниках это не проверено после полного завершения прежних процессов.
- Обмен местами игроков может оставить units с историческими owners или привести к переassign при `autoassign`. Без фактического теста нельзя определить соответствие игрока к сохранённой стороне.
- Одновременный набор peer-снимков может быть неатомарным: в анализируемом коде не найден общий commit manifest/ACK всех peers. Совпадающий quant в логах не доказывает завершённую запись каждого архива.

## Неизвестные значения и решения

До полевого теста неизвестны: точный состав сериализуемого состояния; минимальный достаточный архивный набор; допустимые изменения roster и host; синхронность таймстемпов/quant; влияние campaign/skirmish lobby; поведение при отсутствующем peer; восстановление незавершённого script sequence; требования к локальному пути/профилю; совместимость между patch versions.

Проектное решение P0.5: сохранять отдельно все найденные client archives и host server archive; не выдавать план на загрузку при несовпадении roster/build/mission/mod fingerprint; статус плана оставлять `RESTORE_TEST_PENDING`. Это fail-closed политика эксперимента, а не утверждение о том, как устроена внутренняя загрузка игры.

## Межсессионные данные, которые должны пережить teardown

Минимально нужно исследовать и затем версионированно фиксировать: уникальный checkpoint ID; mission/map ID; game build; точный mod fingerprint; ожидаемый roster и player slot mapping; кто был host; clock/quant на точке; роли архивов; исходные/целевые локальные пути; размеры и SHA-256 архивов; состояние завершения записи и ACK каждого обязательного процесса; экспериментальные результаты и ошибки загрузки. Сейчас исследуемая реализация сохраняет только локальный marker с mission/archive и иногда base/count.

Никакие значения из этого списка не подставляются автоматически в игровой процесс текущим координатором.
