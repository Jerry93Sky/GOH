# Матрица восстановления TEST-A–F

Все тесты требуют записать точные game build, mission/map path, mod fingerprint, participant IDs/slots, host, quant/game time, UTC time и каталог evidence. Перед началом сделать резервные копии обоих профилей. Сравнение проводится с заранее записанными показателями (юниты, ownership, objectives, triggers), а не только с наличием файла.

Полевые сценарии требуют тестовый checkpoint-механизм, разрешённый для использования и установленный вручную в изолированной копии игры. Проект не поставляет игровых бинарников. Все синтетические тесты coordinator отмечены отдельно и не считаются полевыми.

## Общие правила PASS/FAIL

- **PASS:** все требуемые участники загрузили игровую сцену; игрокам назначены ожидаемые подразделения; проверяемые поля и objectives совпали с моментом checkpoint; важный trigger выполнился ровно по ожидаемым правилам; нет desync/drop/error в UI/логах.
- **FAIL:** любая обязательная сторона не загрузилась, потеряны/перепутаны подразделения, состояние/trigger расходится с заданным checkpoint, несовместимый снимок был принят без отказа, либо произошёл crash/desync.
- **INCONCLUSIVE:** не удалось установить состояние/clock, участник отсутствует, запись неполная или логи не позволяют определить результат.
- Хеш файлов фиксирует байты и целостность копии относительно манифеста, но не подтверждает loadability или семантическую корректность игрового состояния.

Для каждого теста создавать уникальный `test_run_id`. Не перезаписывать failed result при повторе: новая попытка получает другой ID. Сохранять игровые логи клиента A/B и локального server, скриншоты/видео, manifest файлов, таблицу состояния до/после и точные шаги. Пути/личные идентификаторы удалить перед передачей.

## TEST-A: Same Session Reload

- **Предпосылки:** два игрока в исторической coop-миссии, локальный server, checkpoint механизм доступен обоим; полный набор файлов зарегистрирован.
- **Действия:** отметить группу A и B, resources, objective, trigger; сохранить checkpoint; изменить позицию/состав и продвинуть миссию; нажать reload тем же лобби/host.
- **Необходимые файлы:** A `coop_ckpt.sav`, B `coop_ckpt.sav`, server `coop_ckpt_srv.sav`; role-specific logs; видео и таблица состояния.
- **Ожидается:** все peers входят в миссию, состояние возвращается к отметке checkpoint, owners/autoassign и trigger продолжают ожидаемо.
- **PASS/FAIL:** общие критерии; отдельно фиксировать, что это same-session baseline и не доказывает session boundary recovery.
- **Диагностика:** checkpoint save/load elapsed time, quant before/after, remapped owner count, trigger serialize/deserialize counters, scene mission path, host auto-restart/lobby status.

## TEST-B: New Lobby, Same Players

- **Предпосылки:** TEST-A прошёл; оба игрока штатно покидают матч, процессы остаются запущены; есть backup profiles и полный архивный комплект.
- **Действия:** завершить старую session до lobby; создать новое coop lobby тем же host, теми же player IDs/order, mission, build, mods; вручную выбрать/подать прежний checkpoint штатным или разрешённым тестовым путём.
- **Необходимые файлы:** комплект TEST-A плюс client/server logs после полного lobby teardown и start.
- **Ожидается:** старые снимки доступны после окончания match, marker/metadata не зависят от старого session object; новый lobby загружает всех игроков в одной точке.
- **PASS/FAIL:** PASS требует подтверждённой загрузки обеих сторон, roster/ownership и состояния checkpoint; невозможность подать snapshot — FAIL для механизма подачи (не формата архива).
- **Диагностика:** что сохранялось между сессиями (archive/marker/roster/clock), новый session ID/host/slot order, archive paths на каждом ПК, auth/join errors, quant and scene logs.

## TEST-C: New Lobby, Changed Player Order

- **Предпосылки:** TEST-B прошёл; checkpoint создан при стабильных player IDs; записаны исходная связь игрок↔slot↔units.
- **Действия:** завершить сессию, создать новое lobby и поменять порядок/слоты игроков, не меняя миссию/build/mods; подать прежний checkpoint.
- **Необходимые файлы:** комплект checkpoint; до/после roster/slot mapping; ownership снимки каждой контрольной группы.
- **Ожидается:** units назначаются по выбранной политике (идентичность игрока либо slot); политика должна быть оговорена до запуска и одинакова для всех повторов.
- **PASS/FAIL:** PASS только если обе группы контролируются оговорёнными игроками, owner IDs не конфликтуют, команда видит одинаковое состояние; случайное автоназначение считается FAIL.
- **Диагностика:** player IDs до/после, slot order, owner remap/autoassign сообщения, client roster, server scheduler/quant.

## TEST-D: Client Crash

- **Предпосылки:** TEST-B пройден при штатном выходе; полный checkpoint подтверждён на A, B и server; evidence копии отделены от игровых профилей.
- **Действия:** после контрольной точки изменить мир; аварийно завершить только B; зафиксировать поведение A и server, завершить старую сессию, перезапустить B, создать новое lobby и загрузить предыдущую полную точку.
- **Необходимые файлы:** все три снимка до crash, сохранения/логи после crash если доступны, crash event/time, новый roster.
- **Ожидается:** система выбирает предыдущую целую точку; не принимает частичный/более новый архив как общий checkpoint; обе стороны получают одинаковую сцену.
- **PASS/FAIL:** PASS если обе стороны восстановлены из заранее зафиксированного набора и контрольные состояния совпали; fallback на неизвестный server-only archive не является PASS.
- **Диагностика:** last completed checkpoint ID, размер/hash каждого архива, file times, per-peer markers, crash timestamp, server lobby state, причина выбора кандидата.

## TEST-E: Missing Peer Snapshot

- **Предпосылки:** coordinator synthetic test; для игры — отдельный негативный прогон на копии evidence, checkpoint с A/server и отсутствующим B.
- **Действия:** при filesystem harness скопировать архивы A+server, опустить каталог B и вызвать `capture`/`plan`. В игре, только если безопасно и разрешено, повторить подачу неполного набора без изменения оригиналов.
- **Необходимые файлы:** source dirs A/server, отсутствующий B явно в expected roster; manifest/plan/report.
- **Ожидается:** manifest `INCOMPLETE`; planner не выдаёт восстановительный набор; UI/экспериментальный loader отказывает безопасно.
- **PASS/FAIL:** harness PASS если статус неполный и нет `RESTORE_TEST_PENDING` плана; игровой PASS если отказ безопасный и оригинальные профили не изменены. Тихий пропуск участника — FAIL.
- **Диагностика:** missing participant/path, список доступных и отсутствующих files, coordinator stderr/JSON, loader logs если применимо.

## TEST-F: Mission Script Continuity

- **Предпосылки:** определить критический script trigger, который ещё не сработал; создать контрольную точку до условия его запуска; записать его предусловия и ожидаемый эффект.
- **Действия:** сохранить, продвинуть миссию до события и записать результат; восстановить checkpoint тем же или новым lobby (зафиксировать какой тест); выполнить условия trigger ещё раз.
- **Необходимые файлы:** полный набор checkpoint, mission ID/version, события/цели до/после, script/trigger diagnostics из доступного log.
- **Ожидается:** trigger остаётся в правильном состоянии и выполняется один раз, событие/подкрепление/цель соответствует восстановленной точке без дублирования или потери.
- **PASS/FAIL:** PASS если trigger исполняется в правильной фазе ровно ожидаемое число раз и обе стороны согласны; stuck/missing/double-fired event — FAIL.
- **Диагностика:** trigger identity and phase, script sequence in progress, elapsed/quant clock, objective state, server/client event logs.

## Текущее состояние

8 unit tests coordinator покрывают только файловые свойства и модель данных. Они не запускают TEST-A–F. При отсутствии установленной игры и второго клиента каждый полевой сценарий остаётся `NOT_RUN`; TEST-E имеет отдельный результат `FILE_HARNESS_ONLY`.
