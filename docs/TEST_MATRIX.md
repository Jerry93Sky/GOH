# Матрица экспериментов P0/P1

## Стенд и критерии

Нужны две отдельные установки/клиента Windows x64 одинаковой версии игры и модов, одна историческая coop-миссия, локальный dedicated server хоста, чистая тестовая копия профилей, запись экрана/логов и доступ к архивам checkpoint. Не использовать рабочую установку как экспериментальную. Перед каждым случаем зафиксировать game build, mission ID, моды/порядок, карту, игроков и роли.

Исходники стороннего checkpoint-мода утверждают, что его Save выдаёт отдельные файлы на peers и локальном server. На P0 это не воспроизведено.

## Минимальная серия

| ID | Сценарий | Артефакты | Что подтверждает |
|---|---|---|---|
| T0 | Vanilla coop, обычный новый старт | версии, список модов, логи, roster | базовое поведение и контрольная группа |
| T1 | A+B в исторической coop-миссии; сохранить тестовый baseline | видео, mission/roster, timestamp | исходное состояние сравнения |
| T2 | Синхронный checkpoint через исследуемый механизм | A/B/server archives, логи с clock и timestamp | фактическое число и завершённость снимков |
| T3 | Продолжить миссию N минут и менять известные сущности: юниты, потери, техника/инвентарь, objective/trigger progress | скриншоты/ручная таблица до сохранения | наблюдаемое состояние «после checkpoint» |
| T4 | Корректно завершить обоих клиентов и server; создать новое coop lobby той же конфигурации; загрузить checkpoint всеми доступными вариантами | результат каждого peer, ошибки, clock, roster | штатный межсессионный restore |
| T5 | Повторить T2, затем аварийно закрыть клиент B до выхода хоста; A создаёт новое lobby | доступность файлов/маркеров и исход загрузки | основной crash recovery сценарий |
| T6 | Раздельные варианты: все peer-local archives; только server archive; archive A для A+B; переставить роли/host при фиксированном roster | все archive hashes и outcomes | необходимы ли уникальные данные каждого клиента |
| T7 | Негативные проверки: отсутствующий/обрезанный архив, несовпадающий build/mod/mission, иной roster | отказ/сообщение; исходная установка неизменна | fail-closed поведение |

### Сравнение состояния

Перед T2 вручную зафиксировать в таблице на каждом участнике: quant clock если доступен, позицию/состав/здоровье контрольных групп, владение юнитами, ресурсы/пополнение, потери, objective progress и состояние триггеров. T3 задаёт отличия от контрольной точки. После T4 сравнить каждый показатель с T2. Снимки на одном peer сами по себе не доказывают синхронность между A/B.

Использовать `tools/compare_snapshot_trees.ps1` только на копиях архива до/после. Совпадающие SHA-256 означают совпадение файловых байтов, но не семантического игрового состояния; разные хеши не означают автоматически desync, так как архив может содержать локальные/player-specific поля.

## Повторяемость и отчёт

Каждый сценарий выполнить минимум три раза после восстановления исходной копии профилей. Хранить каталоги `evidence/<run>/<peer>/<before|after>/`, исходные логи, манифесты хешей и таблицу наблюдений. Для каждого запуска отметить PASS только если все предусмотренные peers загрузили мир, roster/ownership сохранён, указанное состояние совпало с точкой checkpoint и нет блокирующих ошибок. Иначе FAIL с точным симптомом; неподтверждённый результат — INCONCLUSIVE.

## Текущая доступность

В этой среде нет обнаруженной установки GoH и процессов игры, второго клиента тоже нет. T0–T7 не выполнены. Установлен только воспроизводимый файловый comparator; он проверен на синтетических каталогах (раздел final report указывает этот ограниченный тест отдельно).
