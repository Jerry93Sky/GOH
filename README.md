# GOH Coop Recovery

**Автор и сопровождающий:** [Jerry93Sky](https://github.com/Jerry93Sky) · [Исходный код](https://github.com/Jerry93Sky/GOH)

Независимый пользовательский проект для исследования восстановления исторических кооперативных миссий *Call to Arms – Gates of Hell: Ostfront* после вылета или отключения участника. Цель — дать возможность продолжить совместную миссию с последней согласованной контрольной точки. Проект не связан с разработчиками игры и не является их официальным продуктом.

> **V0.2.1 Experimental — `EXPERIMENTAL / GAME TEST PENDING`.** Автоматические тесты и Windows-сборка подтверждены. TEST-A и TEST-B в реальной игре не проводились; восстановление игрового состояния не объявляется работающим.

## Для чего создан проект

Историческая кооперативная кампания может потребовать начать миссию заново, если один из игроков отключился или игра завершилась аварийно. GOH Coop Recovery изучает восстановление после завершения сетевой сессии через новое лобби. Подключение к уже продолжающейся миссии (Hot Rejoin) — отдельная будущая исследовательская задача.

## Возможности

Текущий Recovery Manager умеет обнаруживать/выбирать установку, работать с локальными checkpoint-файлами и manifest, проверять архивы по размеру и SHA-256, наблюдать за файлами и собирать runtime metadata с указанием источника. Он экспортирует отдельные ZIP-пакеты участников, поддерживает локальный импорт без перезаписи файлов, проверяет набор client/server архивов, формирует диагностику и операторские отчёты.

Экспериментальная подготовка marker для нового лобби блокируется, если не совпали роль и источник лога, профиль, архив, владелец, размер или SHA-256 либо отсутствует ручной протокол сопоставления контрольной точки. Client и host-server marker готовятся отдельно. Это файловый preflight; он не загружает и не синхронизирует состояние в игре.

## Состояние разработки

| Версия | Результат |
|---|---|
| V0.1 | Базовый экспериментальный Recovery Manager и файловая проверка |
| V0.2 | Наблюдение за сохранениями, сбор метаданных и peer-пакеты |
| V0.2.1 | Ужесточение выбора источников и marker preflight |
| Следующий этап | Полевые TEST-A/TEST-B на двух игровых клиентах |
| Будущее исследование | Автоматизация восстановления после разрыва; отдельно — Hot Rejoin |

Локальное `checkpoint #N` является счётчиком процесса, а не общим ID. Ручной JSON-протокол фиксирует источники и операторское сопоставление, но **не доказывает** синхронную запись движком. `TEST-A=NOT_RUN`, `TEST-B=NOT_RUN`.

Артефакты доступны ограниченное время; сверяйте checksum `GOHRecoveryManager.exe` из `checksums.sha256` после распаковки.

## Требования

- Windows 10/11 x64 для GUI-сборки.
- Для файловой работы игра не обязательна. Для игровых испытаний требуется установленная *Call to Arms – Gates of Hell: Ostfront*.
- Совместимый Coop Checkpoint устанавливается отдельно пользователем; его DLL и `version.dll` не распространяются этим проектом.
- Для кооперативного испытания у всех участников должны совпадать версии игры, миссия и набор модов.

## Установка

1. Скачайте ZIP из GitHub Actions artifact и распакуйте в отдельную папку, например `C:\GOH-Recovery-Test`.
2. Проверьте SHA-256 `GOHRecoveryManager.exe` по `checksums.sha256`.
3. Запустите `GOHRecoveryManager.exe`; укажите каталог игры при необходимости.
4. Не помещайте программу в каталог игры. Она не устанавливает DLL и не заменяет `version.dll`.
5. До работы с архивами сохраните резервную копию профиля. Подробности: [установка](docs/INSTALL_RU.md) и [первый запуск](docs/FIRST_RUN_RU.md).

## Как пользоваться

1. **Игра:** найдите установку и просмотрите обнаруженные файлы; наличие файла не считается доказательством runtime-совместимости.
2. **Наблюдение:** выберите профиль и вручную укажите точные логи game process, а для хоста — также local server process. Источник каждого значения фиксируется.
3. **Контрольные точки:** проверьте manifest и целостность каждого client/server архива; создайте отдельные пакеты участников.
4. **Восстановление:** импортируйте только нужные локальные архивы, проверьте группу и ручной consistency protocol. Для хоста client и server marker готовятся отдельными операциями.
5. **Диагностика:** экспортируйте отчёты и зафиксируйте фактическое наблюдение. Только игровой тест может подтвердить загрузку.

Краткая последовательность с другом приведена в [первом запуске V0.2.1](docs/P1_C1_FIRST_RUN_RU.md), навигация по материалам — в [индексе документации](docs/INDEX_RU.md).

## Проверка восстановления

- **TEST-A:** на двух клиентах создать checkpoint в одной живой кооперативной сессии, сохранить отдельные клиентские и host-server архивы, проверить штатную загрузку и сравнить игровое состояние.
- **TEST-B:** после TEST-A завершить сессию, собрать и проверить снимки, создать новое лобби той же миссии и проверить загрузку на всех участниках; фиксировать objective/trigger state, quant/game time и владение подразделениями.

Полные протоколы: [TEST-A](docs/TEST_A_RU.md), [TEST-B](docs/TEST_B_RU.md). Пока оба теста имеют статус `NOT_RUN`.

## Архитектура

- `recovery_coordinator.py` — локальные snapshots, manifest и проверка файлов.
- `recovery_harness.py` — peer-пакеты, импорт/экспорт, marker preflight и ручной consistency protocol.
- `runtime_metadata.py` — чтение известных игровых логов и хранение provenance.
- `archive_path_resolver.py` — консервативное сопоставление virtual archive path с точным локальным профилем.
- `goh_recovery_manager.py` — русский Tk GUI.
- `.github/workflows/windows-v0.2.1.yml` — тесты, сборка Windows EXE, smoke test и ZIP artifact.

## Ограничения и совместимость

Результат зависит от конкретной версии игры, Coop Checkpoint, профиля и содержимого миссии; требуется реальная проверка на выбранном build. Известные блокеры и границы эксперимента описаны в [P1-C.1 results](docs/P1_C1_RESULTS.md) и [рисках/лицензиях](docs/RISKS_AND_LICENSES.md).

В проекте нет игровых hooks или собственной DLL; он не меняет сетевой протокол, игровые ресурсы, аутентификацию или защитные проверки. Неизвестные поля не подставляются по догадке. Стабильного восстановления между сессиями пока не заявлено.
